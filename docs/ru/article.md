# JPA Entity != DDD Entity

## Введение

Большинство Java-разработчиков уверены, что DDD Entity — это обычная JPA Entity с бизнес-методами. Именно так выглядит почти каждый пример в интернете. К сожалению, именно с этой идеи часто начинается постепенная деградация доменной модели.

Когда вы начинаете изучать Domain-Driven Design, одна из первых ловушек, в которую попадают почти все — это путаница между DDD Entity и JPA Entity. Почти каждый учебный пример показывает DDD-сущность в виде JPA-сущности: один и тот же класс одновременно и домен, и отражение базы данных. Выглядит удобно, но на деле это большая ошибка.

Она неочевидна на старте, но по мере роста проекта неизбежно приводит к проблемам: домен обрастает инфраструктурными ограничениями, инварианты размываются, а рефакторинг превращается в кошмар. Давайте разберёмся, почему JPA Entity и DDD Entity — это принципиально разные вещи, и почему их нельзя смешивать в одном классе.

## Что такое JPA-сущность на самом деле
JPA-сущность — это проекция таблицы реляционной базы данных на объект в вашей программе. Это сугубо persistence model: её задача — сохранять и читать данные, не более.

Вот типичный пример:

```java
@Entity
@Table(name = "orders")
public class Order {
    @Id
    @GeneratedValue
    private Long id;

    @Column(name = "status")
    private String status;

    @Column(name = "total")
    private BigDecimal total;

    public Long getId() { return id; }
    public void setId(Long id) { this.id = id; }

    public String getStatus() { return status; }
    public void setStatus(String status) { this.status = status; }

    public BigDecimal getTotal() { return total; }
    public void setTotal(BigDecimal total) { this.total = total; }
}
```

Это анемичная модель: геттеры, сеттеры, никакого поведения. Она полностью подчинена правилам JPA-провайдера — `@Entity`, `@Table`, `@Column` диктуют, как класс будет отображён на базу данных. Здесь нет места бизнес-правилам, только данные и доступ к ним.

JPA решает исключительно инфраструктурную задачу — преобразование объектов в строки таблиц и обратно. Его цель — минимизировать код доступа к данным. DDD же занимается совершенно другой проблемой: моделированием поведения предметной области. Когда один класс одновременно пытается решать обе задачи, он начинает зависеть сразу от двух разных наборов требований.

## Что такое DDD-сущность на самом деле
Согласно Эрику Эвансу, автору книги Domain-Driven Design (2003), Entity — это тактический паттерн, описывающий объект, который определяется в первую очередь своей идентичностью, а не атрибутами. Идентичность проходит через время и разные представления объекта: какие бы изменения ни происходили с атрибутами — это всё тот же объект.

На практике DDD-сущность — это POJO: обычный Java-объект без каких-либо зависимостей от фреймворков. Никаких `@Entity`, `@Table`, `@Column` — только бизнес-правила и инварианты.

**Инварианты** — это условия, которые всегда должны быть соблюдены. Сущность сама следит за своей целостностью и не позволяет внешнему коду привести себя в некорректное состояние.

**Бизнес-правила** живут внутри класса, а не снаружи в сервисах. Нельзя просто взять и изменить `status` — нужно пройти через метод, который проверит допустимость перехода.

Вот тот же Order, но уже как DDD-сущность:

```java
public class Order {
    private final OrderId id;
    private OrderStatus status;
    private Money total;
    private final List<OrderItem> items;

    public Order(OrderId id, List<OrderItem> items) {
        if (items == null || items.isEmpty()) {
            throw new IllegalArgumentException("Order must have at least one item");
        }
        this.id = id;
        this.items = new ArrayList<>(items);
        this.status = OrderStatus.NEW;
        this.total = calculateTotal();
    }

    public void markAsPaid() {
        if (status != OrderStatus.NEW) {
            throw new IllegalStateException("Only NEW orders can be marked as paid");
        }
        this.status = OrderStatus.PAID;
    }

    public void markAsShipped() {
        if (status != OrderStatus.PAID) {
            throw new IllegalStateException("Only PAID orders can be shipped");
        }
        this.status = OrderStatus.SHIPPED;
    }

    // инвариант: total всегда равен сумме позиций
    private Money calculateTotal() {
        return items.stream()
                .map(OrderItem::subTotal)
                .reduce(Money.ZERO, Money::add);
    }

    public OrderId id() { return id; }
    public OrderStatus status() { return status; }
    public Money total() { return total; }
    public List<OrderItem> items() { return Collections.unmodifiableList(items); }
}
```

Что здесь изменилось по сравнению с JPA-версией:
- **Никаких аннотаций** — чистый POJO, не привязанный к инфраструктуре
- **Инварианты защищены** — конструктор гарантирует, что заказ не может быть пустым
- **Бизнес-правила внутри** — `markAsPaid()` и `markAsShipped()` проверяют допустимость переходов; нельзя просто сделать `setStatus()`
- **Идентичность своя** — `OrderId` это не `Long` от БД, а value object со своим смыслом

И главное: такую модель можно тестировать **без базы данных**. Никаких `@DataJpaTest`, никаких поднятий контейнеров. Обычный JUnit — быстро, дёшево, надёжно:

```java
@Test
void shouldNotAllowShippingUnpaidOrder() {
    Order order = new Order(new OrderId(UUID.randomUUID()), List.of(anItem()));

    assertThrows(IllegalStateException.class, order::markAsShipped);
}
```

Как только мы добавили бизнес-правило в сущность — мы можем тут же написать на него тест. Никаких репозиториев, никаких сервисов, никакой инфраструктуры. В случае же с JPA-подходом, чтобы протестировать то же самое правило, вам пришлось бы сначала реализовать репозиторий, затем сервис, и только потом писать тест — скорее всего, интеграционный, с поднятой базой данных. Три дополнительных слоя и в разы больше времени.

Писать тесты — не самое приятное занятие для многих разработчиков. И чем сложнее и дольше процесс написания теста, тем выше соблазн его пропустить. DDD-сущность убирает все препятствия: тест пишется мгновенно, запускается мгновенно, и шанс, что он действительно будет написан, резко возрастает.                                                                   

## Почему их опасно смешивать в одном классе
Иногда возникает соблазн докинуть всё, что есть в DDD-сущности, в JPA-сущность. И это может сработать, но только в начале, а потом появляется куча проблем.

### Два хозяина одного класса

JPA требует одного, DDD — прямо противоположного. JPA хочет пустой конструктор, открытые геттеры и сеттеры, доступ к полям для проксирования. DDD — инкапсуляцию, минимум публичных методов и защиту инвариантов. Когда вы пытаетесь усидеть на двух стульях, получается примерно такой кентавр:

```java
@Entity
@Table(name = "orders")
public class Order {
    @Id
    @GeneratedValue
    private Long id;

    @Column(name = "status")
    @Enumerated(STRING)
    private OrderStatus status;

    @Column(name = "total")
    private BigDecimal total;

    // JPA требует пустой конструктор
    protected Order() {
    }

    // А это уже для DDD
    public Order(List<OrderItem> items) {
        if (items == null || items.isEmpty()) {
            throw new IllegalArgumentException("Order must have at least one item");
        }
        this.status = OrderStatus.NEW;
    }

    // Бизнес-методы пытаются защитить инварианты...
    public void markAsPaid() {
        if (status != OrderStatus.NEW) {
            throw new IllegalStateException("Only NEW orders can be marked as paid");
        }
        this.status = OrderStatus.PAID;
    }

    // ...но сеттеры всё равно торчат наружу
    public void setStatus(OrderStatus status) { this.status = status; }
    public void setTotal(BigDecimal total) { this.total = total; }

    // геттеры, геттеры, геттеры...
}
```

У этого класса сразу несколько проблем:

**Инварианты ничем не защищены.** Да, у вас есть `markAsPaid()`, но любой разработчик может дёрнуть `setStatus()` в обход. Компилятор не жалуется, линтер не жалуется — инвариант нарушен, никто не заметил.

**Зависимость от инфраструктуры в домене.** Аннотации `@Entity`, `@Table`, `@Column` диктуют, как доменный объект будет храниться в базе. Измените схему БД — придётся менять домен. Измените домен — рискуете поломать маппинг. Single Responsibility Principle нарушен: у класса две совершенно разных причины для изменений.

**Тесты не напишешь без БД.** Чтобы протестировать бизнес-правило, вам нужен EntityManager, транзакция, база. Медленно, громоздко, и соблазн забить на тесты растёт с каждым новым правилом.

**Это работает только на старте.** Когда проект маленький, кажется, что «ну тут всего три поля, чё там». Но бизнес-логика имеет свойство накапливаться. Через полгода у вас уже десятки методов, часть переходов статусов реализована через бизнес-методы, часть — через `setStatus()` в сервисе, и распутать этот клубок становится почти невозможно.

## Выводы

JPA Entity и DDD Entity могут выглядеть одинаково, но решают совершенно разные задачи. Первая описывает, **как данные хранятся**, вторая — **как ведёт себя бизнес**. Пока проект небольшой, объединение этих ролей в одном классе кажется удобным и даже естественным. Но по мере роста системы эта «экономия» начинает обходиться дорого: доменная модель становится зависимой от инфраструктуры, инварианты нарушаются всё чаще, а тестирование и рефакторинг требуют всё больше усилий.

Это не означает, что любой проект обязан разделять доменную и persistence-модели. Для простого CRUD-приложения использование одной JPA-сущности может быть вполне оправданным компромиссом. Однако если вы строите систему, в которой доменная логика действительно сложна, имеет смысл провести границу между моделью предметной области и моделью хранения данных как можно раньше.

Хорошая эвристика проста: если вы ловите себя на мысли, что добавляете в доменную сущность аннотации, сеттеры или другие элементы исключительно потому, что этого требует ORM, — скорее всего, вы уже смешиваете две разные ответственности.

DDD не запрещает использовать JPA. Он лишь предлагает не путать инструмент хранения данных с моделью предметной области. И чем сложнее становится бизнес, тем ценнее оказывается это разделение.

JPA — это способ хранить данные.
DDD — это способ моделировать бизнес.

Пока эти две роли выполняет один класс, кажется, что всё просто. Но как только бизнес становится сложнее, выясняется, что удобство было лишь временным. Именно поэтому опытные DDD-команды разделяют модель хранения данных и модель предметной области — не из любви к «чистой архитектуре», а потому что это позволяет системе оставаться понятной и управляемой по мере роста.
